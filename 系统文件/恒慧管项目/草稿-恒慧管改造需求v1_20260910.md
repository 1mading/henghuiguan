| P1-5 | 补验证记录、业务反馈、遗留问题 |
| P1-6 | 统一阶段模板（**已提供模板库**：默认 WMS；另有标准过程组；可从项目另存） |

**降级 / 基本已有**

| 编号 | 说明 |
|---|---|
| P2-8 | 角色和权限矩阵**已有**；本项只做抽查：按钮是否真按矩阵显隐，**不新建角色体系** |

**明确不做**：模板库、版本管理。

### 1.4 改造原则

1. **不破坏现有数据**：新字段可空，老数据兼容。  
2. **以本工作区现网为准**：实施前若生产与副本不一致，以生产实测为准。  
3. **单一权威源**：项目/任务真值在恒慧管；原定快照与变更原因写在系统内。  
4. **权限双轨**：登录态走现有角色+矩阵；对外走作用域 Key（增强，不另起炉灶）。

## 二、改造清单

### 🔴 P0-1：原定 vs 调研后确认（日期基线）

**需求**：对齐会要求能看出「原定节点」和「后来确认/调整后的节点」；现在改日期会把旧值盖掉。

**现状**：只有一套日期，改即覆盖。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据 | 任务增加：原定开始、原定截止、变更原因；项目增加：原定最终完成日、变更原因 |
| API | PATCH 任务/项目日期时：第一次改动前把旧值写入「原定」；之后改动写入变更日志；可查 history |
| 界面 | 详情页并排显示「原定 \| 当前」；改日期时弹窗：确认是否保留原定 + **必填变更原因**（可选写影响说明） |

**工作量**：小  

**验收**：
- 改过日期后，仍能看到原定值  
- 详情页有「原定 vs 当前」  
- 无变更原因不能随便盖掉已有原定（产品规则按上表）

---

### 🔴 P0-2：当前阶段跟随里程碑（弱化版）

**需求**：项目推进到哪一阶段，应能从里程碑进度看出来，少靠纯手工改状态。

**现状**：可手填 `currentPhase`；项目 `status` **不会**随里程碑自动变。

**改造方案（本版定稿口径）**：

| 层 | 改动 |
|---|---|
| 数据 | **不**把 `projects.status` 强行改成十一段英文枚举；继续用现有 status + `currentPhase` |
| 逻辑 | 里程碑完成时：自动建议/更新 `currentPhase`（取「当前未完成的最近里程碑」名称或模板阶段名）；提供「同步当前阶段」按钮 |
| 界面 | 项目详情显示：当前阶段、由哪条里程碑驱动、上次同步时间 |

**说明**：等 P1-6 统一模板到位后，再细化「阶段名 ↔ 里程碑」映射；**禁止**在模板未定时大改 status 枚举。

**工作量**：中（小于原「十一段 status 自动切」方案）  

**依赖**：有默认里程碑即可开工；与模板完美对齐等 P1-6  

**验收**：
- 里程碑完成后，当前阶段能更新或一键同步  
- 页面能看出「阶段来自哪条里程碑」

---

### 🔴 P0-3：问题 / 风险闭环

**需求**：事实、原因、影响、方案、需要谁支持、跟进人、预计处理日、验收结果——要能闭环，不能只写一句 blocker。

**现状**：仅 `blocker` 文本。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据 | 新建问题表（挂项目，可选挂任务）：标题、状态、事实/原因/影响/方案/支持人/负责人/预计关闭日/验收信息等 |
| API | 增删改查 + 按项目筛选 |
| 界面 | 项目详情增加「问题/风险」页签：列表、详情、状态流转；写 blocker 时可提示「升级为问题」 |

**工作量**：大  

**验收**：
- 能建问题并流转到关闭（关闭需验收信息）  
- 项目页能看到列表与是否闭环  

---

### 🟡 P1-4：项目一键交接

**需求**：不做模板库/版本管理；交接 = 项目详情按钮 → 选人 → 改**项目负责人** → 留记录。

**现状**：只有任务转派，没有项目级交接动作。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据 | 项目增加交接记录数组（从谁、到谁、时间、备注） |
| API | `POST .../handover`：改负责人字段（现网 `manager` / 负责人，**不是**任务 assignee）并追加记录 |
| 界面 | 项目详情「交接」按钮 → 选人 + 备注 → 确认；下方可看历史 |

**工作量**：小  

**验收**：
- 有交接按钮；交接后负责人变更且记录可查  

---

### 🟡 P1-5：交付验证补全

**需求**：阶段要有交付物 + 验证记录 + 业务反馈 + 遗留问题。

**现状**：里程碑已有交付物、验收标准等；**缺**验证过程、业务反馈、遗留。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据 | 在现有交付相关字段旁增加：验证记录、业务反馈、遗留问题（可空） |
| API | PATCH 任务/里程碑可写上述字段 |
| 界面 | 详情页分块填写；列表可用图标/计数提示「是否齐备」 |

**工作量**：小  

**验收**：
- 详情能填验证/反馈/遗留  
- 列表能看出是否齐备  

---

### 🟡 P1-6：统一阶段模板（待提供）

**需求**：黄艳+刘易牵头的统一阶段（如：启动/调研/蓝图/配置/测试/培训/上线/运维/验收）。

**现状**：仅有系统默认建里程碑，不能选「部门统一模板」绑定。

**改造方案**（模板内容到位后再细改）：

| 层 | 改动 |
|---|---|
| 数据 | 阶段模板表；项目可绑定模板 ID |
| API | 模板列表；项目绑定模板 |
| 界面 | 创建/编辑项目时选模板，并按阶段生成里程碑 |

**状态**：⚠ **等先生提供模板内容（黄艳/刘易成果）后再开工**

---

### 🟡 P1-7：对外 Key 按项目收紧（增强现有能力）

**需求**：给外部 AI/协作方时，只能动允许的项目，不能拿到全局钥匙。

**现状**：**人员作用域 Key 已有**（跟人、按他权限看相关项目）；草稿原先写的「从零新建另一套 Key 表」**不再采用**。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据 | 在现有 api_keys / 作用域 Key 上增加可选：`projectIds` 读写白名单（空 = 仍按「相关项目」人员权限） |
| API | 已有 scope 中间件上增加：若配置了白名单，则 projectId 不在列表 → 403 |
| 界面 | **人员档案**签发/编辑 Key 时，可勾选项目（只读/可写）；不必另做一套「对外 Key 后台」 |

**兼容**：全局 `API_KEY` 保留兼容期。  

**验收**：
- 配置了白名单的 Key，访问名单外项目 → 403  
- 未配白名单的人员 Key，行为与现网「相关项目」一致  

---

### 🟢 P2-8：角色与按钮一致性（治理，非新建）

**需求**：经理和执行人员看到的操作应有差别。

**现状**：`gm/admin/manager/staff` + 权限矩阵**已存在**。

**本项做什么**：
- 抽查关键页（项目详情、人员档案、系统设置等）按钮是否按矩阵显隐  
- 发现不一致则改前端判断，**不**新增一套 role ENUM  

**验收**：抽查清单通过；经理不能改无权项目。

---

### ⚫ 不做：模板库 / 版本管理

交接走 P1-4；不做模板库与版本管理。

## 三、数据模型变更汇总

| 表 | 操作 | 说明 |
|---|---|---|
| 任务 | 增字段 | 原定开始/截止、变更原因；验证/反馈/遗留（交付物相关在现有字段上扩展） |
| 项目 | 增字段 | 原定最终完成日、变更原因、交接记录；可选 stage_template_id |
| 问题 | 新建表 | 见 P0-3 |
| 阶段模板 | 新建表 | 见 P1-6，等模板内容 |
| 作用域 Key | 扩展 | 可选项目白名单（P1-7）；**不**新建平行 external_api_keys 主方案 |
| users.role | **不强制新建** | 现网角色已有；P2-8 只做矩阵落地 |

## 四、API 变更汇总

| 方法 | 路径/点 | 说明 | 依赖 |
|---|---|---|---|
| PATCH | 任务/项目 | 原定日期、变更原因、验证/反馈/遗留 | P0-1 / P1-5 |
| POST | 项目 handover | 一键交接负责人 | P1-4 |
| POST | 项目 sync-phase（或等价） | 按里程碑同步 `currentPhase` | P0-2 |
| CRUD | issues | 问题闭环 | P0-3 |
| GET | history | 日期等变更日志 | P0-1 |
| GET/绑定 | stage-templates | 阶段模板 | P1-6 |
| 中间件 | 作用域 Key | 可选项目白名单校验 | P1-7 |
