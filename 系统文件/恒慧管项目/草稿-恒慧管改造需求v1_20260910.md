## 一、背景与目标

### 1.1 触发原因

- **9-09 晚 陈璇召集"信息部门项目对齐会"**（25~30 个项目），明确三大决策：① 黄艳+刘易牵头统一项目阶段模板；② 计划必须细化+核对工作日历；③ 变更主动汇报+计划展示区分"原定 vs 调研后确认"二段。
- **9-10 早 信息中心 12 项管理要求**（`05-公共资源库/汇报内容/两级经理统一要求.html` / `管理要求_王元斌.html`）固化为本部门项目管控基线。
- **9-10 先生逐条对齐**：19 条要求中 10 条已满足（含钉钉日志+线下抄送+线下审批外部满足），9 条待处理改造。

### 1.2 当前恒慧管能力（基线）

| 维度 | 现状 |
|---|---|
| 任务层级 | 里程碑（M0~M7）+ 二级子任务 可建 |
| 日期字段 | `planStartDate` / `dueDate` 各一套，**改即覆盖** |
| 任务状态 | `todo` / `doing` / `done`（**仅三态**） |
| 权限（生产登录态） | **登录账号 + 业务域 key**，已区分总经理/部门经理/执行人员（person_file 参照钉钉通讯录） |
| 权限（external） | **单 X-Api-Key 字符串对比全放行**（源码 c9df468 路径） |
| 项目字段 | PATCH 仅 `currentPhase/nextPlan/blocker/desc/endDate` 持久化；`objective/value/scope/outOfScope` 源码层面静默忽略，但 9-10 实测 WMS 库里有值（前端手填能进，**生产后端可能已放开**） |

### 1.3 缺口结论

- ✅ **满足（10 条）**：1/3/5/9/10/11/15/16/17/19（10/11/15 由钉钉日志+线下抄送+线下审批外部满足）
- ⏳ **待处理（9 条）**：2/4/6/7/8/12/13/14（详见第二章）

### 1.4 改造原则

1. **不破坏现有数据**：所有新增字段允许为空，老数据兼容。
2. **生产后端优先于源码副本**：本文档以源码 c9df468 为基线，但字段生效与否请以生产实测为准（特别是 `objective/value/scope`）。
3. **单一权威源**：项目/任务真值源 = 恒慧管；变更基线快照、本地主表为辅助。
4. **角色与权限双轨**：登录态权限走现有角色体系不动；external API 路径新增 scope 校验。

## 二、改造清单（9 条）

### 🔴 P0-1：#4 原定 vs 调研后确认 二段日期基线留存

**需求**：陈璇对齐会明确要求计划展示"原定节点"与"调研后确认节点"两段；当前 `planStartDate/dueDate` 改即覆盖，**无基线留存**。

**现状**：单值覆盖。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | `tasks` 表新增 3 列：`original_plan_start_date DATE NULL`、`original_due_date DATE NULL`、`change_reason TEXT NULL`；`projects` 表对应新增：`original_end_date DATE NULL`、`change_reason TEXT NULL` |
| API | `PATCH /external/tasks/:id` 接受 `originalPlanStartDate/originalDueDate/changeReason`（首次写入快照）；新增 `GET /api/workbuddy/history?type=task&id=<tid>` 查变更日志 |
| UI | 任务详情/项目详情增加"原定计划"区块（灰显）；修改日期时弹"是否覆盖原计划"确认 |
| 触发逻辑 | 任意 PATCH 写入 `planStartDate/dueDate` 时，若原值为空则写入快照；若已有快照则记录到 history |

**工作量**：小（后端 1 文件 + 1 接口，前端 1 视图 + 1 弹窗）

**依赖**：无

**验收**：
- 任意 PATCH 日期后，原始值能在 history 接口查到
- 任务详情页能看到"原定 vs 当前"对比

---

### 🔴 P0-2：#6 项目 status 跟随里程碑自动联动

**需求**：项目层 status 根据里程碑完成进度自动切换（M0 完成 → 切到 M1 推进中；M1 完成 → 切到 M2）。

**现状**：项目 status 与里程碑进度无关联，依赖手工。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | `projects` 表 `status` 字段扩展为字符串枚举：`planning / selecting / contracting / kickoff / blueprinting / developing / testing / going_live / accepted / on_hold / closed`（**注：枚举值待 #2 统一阶段模板定稿后微调**） |
| API | `POST /external/projects/:id/sync-status`（手动触发）；后端 hook：当 `tasks` 的 `isMilestone=true` 任务 status 变 `done` 时，自动检查所属项目并按映射规则切 status |
| UI | 项目详情页 status 显示当前阶段 + 上次切换时间 + 触发里程碑 |
| 映射规则（默认） | 最后一个未 done 的里程碑决定项目 status；所有里程碑 done → `accepted`；如有 `on_hold` 标志 → 暂停 |

**工作量**：中（后端 hook + 映射规则表，前端 1 组件）

**依赖**：#2（统一阶段模板定稿前用默认映射）

**验收**：
- M0 子任务全 done → 项目 status 自动切 `selecting/contracting/kickoff` 之一（按 M0 描述判断）
- M1 子任务全 done → 项目 status 切 `blueprinting`
- 所有里程碑 done → `accepted`

---

### 🔴 P0-3：#8 问题/风险闭环（独立 issue 实体）

**需求**：陈璇对齐会 todos + HTML 12 项第 12 条都要求问题/风险闭环：事实/原因/影响/方案/支持/跟进人/预计处理日/验收结果。

**现状**：仅 `blocker` 单字段，不够。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | 新增 `issues` 表（独立实体）：`id / projectId / taskId? / title / status(open/in_progress/resolved/verified/closed) / fact / cause / impact / solution / supporter / assignee / expectedCloseDate / verifiedAt / verifiedBy / closedAt / createdAt / updatedAt` |
| API | `POST /external/issues`、`PATCH /external/issues/:id`、`GET /api/workbuddy/issues?projectId=<pid>&status=<s>`；关联 project 或 task |
| UI | 项目详情页增加"问题/风险"Tab；列表 + 详情；状态流转按钮（手动切 + 校验 verifiedAt） |
| 触发 | `tasks.blocker` 写入时，提示"是否升级为 issue"（一键创建） |

**工作量**：大（独立实体 + 完整 CRUD + 前端列表/详情/流转）

**依赖**：无

**验收**：
- 能为项目/任务创建 issue
- issue 状态流转有审计（closed 必填 verifiedAt/verifiedBy）
- 项目详情页能看到 issue 列表与闭环状态

### 🟡 P1-4：#12 一键交接按钮（项目详情页）

**需求**：模板库/版本管理**不做**；交接 = 项目详情页加按钮 → 选人 → 改 assignee + 写交接记录。

**现状**：交接无专门动作，靠口头/邮件。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | `projects` 表新增：`handover_records JSON NULL`（数组元素：`{from, to, at, note}`） |
| API | `POST /external/projects/:id/handover` body `{to: userId, note}` → 改 `assignee` + append `handover_records` |
| UI | 项目详情页右上角加"交接"按钮 → 弹窗（选人 from 钉钉通讯录 + 备注）→ 确认；下方显示历史交接记录 |

**工作量**：小（前端 1 按钮 + 后端 1 接口）

**依赖**：#13（多角色管理可顺便实现选人组件）

**验收**：
- 项目详情页能看到"交接"按钮
- 点击后能选人+填备注 → 确认 → assignee 切换、记录追加
- 交接记录可查询

---

### 🟡 P1-5：#7 交付物+验证记录

**需求**：HTML 12 项 04/05 要求每个阶段有"交付物 + 验证记录 + 业务反馈 + 遗留问题"。

**现状**：仅 `desc` 单字段。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | `tasks` 表新增：`deliverable_url VARCHAR(500) NULL`、`verification TEXT NULL`、`feedback TEXT NULL`、`leftover TEXT NULL` |
| API | `PATCH /external/tasks/:id` 接受上述 4 字段 |
| UI | 任务详情页增加 4 个结构化区块（URL 字段、文本字段），与 desc 区分 |

**工作量**：小（后端 4 列 + 前端 4 区块）

**依赖**：无

**验收**：
- 任务详情页能填交付物 URL/验证记录/业务反馈/遗留问题
- 列表视图能展示交付物是否齐备（图标/计数）

| UI | 项目创建/编辑时选模板；里程碑按模板阶段自动初始化 |

**工作量**：中（取决于模板复杂度）

### 🟡 P1-7：#14 按项目权限（external API scope）

**需求**：给外部人（朱贵乔/魏总 AI 等）限定项目的读写/只读权限。

**现状**：external API 单 Key 全放行；登录态已有角色权限（不动）。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | 新增 `external_api_keys` 表（`id / key_hash / name / scopes JSON{read:[projectIds], write:[projectIds]} / createdAt / expiresAt / createdBy`） |
| API | `requireExternalApiKey` 中间件注入 `req.apiScope`；`/external/*` 路由对 projectId 做 scope 校验（不在 scope 列表 → 403） |
| UI | 后台"对外 API Key 管理"页（admin 角色可见）：增/删/改 Key + 选项目 scope |
| 兼容 | 旧 `API_KEY` 环境变量保留兼容期；新 Key 默认 scope=空（拒绝所有），按需授权 |

**工作量**：中（中间件改造 + Key 管理 UI）

**依赖**：无（独立于其他改造）

**验收**：
- 用限定 projectId 列表的 Key 调 `/external/projects/:id`，projectId 不在 scope → 403
- admin 能在后台管理 Key
- 旧 Key 兼容期内仍可用

---

### 🟢 P2-8：#13 多角色管理（登录账号侧 role 字段）

**需求**：现状角色 = person_file 区分总经理/部门经理/执行人员；功能上不区分（UI 一视同仁）。

**改造方案**：

| 层 | 改动 |
|---|---|
| 数据模型 | `users` 表新增 `role ENUM('admin','manager','member')`（或与现有 `person_file.role` 复用） |
| API | `GET /api/workbuddy/me` 返回 role；前端按 role 路由+按钮可见性 |
| 矩阵 | admin: 全权；manager: 看所辖项目+审批；member: 看/改自己项目 |

**工作量**：中（涉及前端全站权限）

**依赖**：⚠ 现有 `person_file.role` 字段是否已存在需调研

**验收**：
- 不同 role 登录看到的导航/按钮不同
- manager 不能修改其他部门项目
